## 1. Routing model
Observed public routing patterns:
- Home: /
- Static page aliases: /trang-chu.html, /gioi-thieu.html, /tai-game.html
- News detail: /news.php?id=N
- Forum index: /forum/app/forum-N.html
- Forum query-style list: /forum/app/index.php?for=forum&do=list&uid=...&p=0&sz=15

This indicates a legacy content-site routing pattern rather than a modern React SPA route map.

## 2. Component structure

  - Footer
- Pages

- Shared UI
  - NavButton

  - BackToTopButton
  - ForumTopicItem

## 3. State management
Public evidence suggests a traditional server-rendered site, not a fully client-side state store.
Recommended modern reconstruction:
- Local app state for navigation and UI toggles
- Static or mocked data store for page content
- No need for a complex centralized state manager unless the app becomes interactive

For a small-site reconstruction, a simple state model is sufficient:
- route state
- selected page data
- filter/category state
- scroll-state for back-to-top

## 4. Service layer
Suggested public service structure:
- contentService
  - getHomePageData()
  - getNewsById(id)
  - getGuideById(id)
  - getForumIndex(page)
- assetService
  - resolveBannerAsset()
  - resolveButtonAsset()
  - resolveThumbnailAsset()
- rankingService (optional / placeholder until route confirmed)
  - getTopList(type)

Important: do not implement ranking service endpoints without public evidence.

## 5. Data flow
Public flow pattern:
- Route is chosen based on URL
- Content data is loaded from a local data source or mocked JSON
- Page-specific component renders the content
- Static assets and images are bound to the page using URL references
- Forum list pages derive title and metadata from topic data

## 6. Backend requirements
From evidence, the public site appears to be generated by PHP-driven content pages and static assets. For a reconstruction, a minimal independent backend is enough:
- static site or local JSON content store
- optional lightweight Node/PHP service for page generation
- no private auth layer required for public pages

## 7. Constraints
- No admin flow is verified by public inspection
- No payment flow is verified by public inspection
- No private user-account logic is confirmed for public reconstruction
- Ranking routes are not fully verified and should remain explicit placeholders in the project architecture until more public evidence is gathered

## 8. Recommended implementation approach
- Prefer a static/data-driven architecture over a database-heavy configuration
- Keep separate forum and portal UI shell
- Reuse simple page templates but do not collapse all URLs into a single generic template without category handling
- Use public and verifiable content only
- Keep placeholders for unverified ranking and advanced search features

## 9. Implemented architecture

The independent implementation uses React, Vite, and React Router. It preserves
the surveyed public URL forms: `/`, `/trang-chu.html`, `/gioi-thieu.html`,
`/tai-game.html`, `/news.php?id=N`, and `/forum/app/forum-N.html`. The production
host must rewrite these paths to `index.html` for client-side routing.

Page components live in `src/pages/`; shared shell, article-card, and ranking
components live in `src/components/`; confirmed display metadata is in
`src/data/content.js`. There is no backend or remote content service. Route
selection and forum/ranking controls use local React/router state.

The homepage ranking controls show a no-data message because ranking records
and endpoints were not confirmed. Forum topic entries are read-only; login,
registration, and password recovery controls are disabled because no authorized
account backend was available. Download version metadata is shown without
fabricated download targets. Full article body content and source artwork remain
absent pending reuse authorization.

Search, forum thread details, topic submission, authenticated account actions,
and ranking data are not implemented because the available public evidence does
not establish them. See `TEST_REPORT.md` for validation results.
